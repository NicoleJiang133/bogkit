# Blind discovery: authoritative DNS change-admission gate

## Ordered trail before component-source inspection

1. Read the assigned `BRIEF.md` completely.
2. Read the public root `README.md`.
3. Read the four public examples (`starter`, `timeseries`, `chat`, and `search`), including each example manifest and main program.
4. Wrote this note before opening any Fold, ESE, or ANNy source or internal documentation.

## Initial understanding

The requested artifact is an offline, advisory admission gate between two directory snapshots of BIND-style zone files. It must parse a deliberately bounded master-file subset, produce stable canonical record identities, compare only policy-selected zones, apply explicit delegation/glue, alias, TTL, apex, SOA-serial, and supplied-baseline rules, and atomically replace a JSON report only after all selected inputs succeed. It must never deploy or query DNS.

The hard requirements are mostly parser, filesystem-containment, resource-accounting, deterministic serialization, and publication-boundary work. Correct refusal is as important as correct acceptance: unsupported or malformed input, containment violations, cycles, and expansion limit violations must block without replacing an earlier report.

## Existing baseline

The existing release job runs `named-checkzone` per changed zone and reviewers manually inspect semantic diffs. That checker remains authoritative for syntax and the current deployment pipeline remains unchanged. This prototype therefore must consume supplied checker results, preserve every checker failure as a block, and provide narrowly declared semantic evidence. It is not a replacement parser claim and cannot establish Internet reachability.

The comparison oracle must be separate from the implementation: checked-in literal manifests and verdict tables, plus black-box fixtures, rather than expectations generated by the gate itself.

## Component-use hypothesis

- **Fold:** plausible only if its transactional materialized views materially simplify comparing a continuing stream of zone mutations. The public examples show durable insertion/retraction pipelines and consistent snapshots. The brief, however, defines a bounded one-shot comparison whose publication must occur only after complete parsing. A plain in-memory sorted representation is likely smaller, easier to bound, and easier to make byte-deterministic. I will inspect the minimum public API/documentation needed to test whether Fold offers a clear safety or implementation advantage; otherwise I will reject it for this prototype.
- **ESE:** no sane initial fit. Static text embeddings cannot prove DNS record identity, path containment, RFC 1982 arithmetic, or policy verdicts. Approximate semantic similarity would weaken exactness.
- **ANNy:** no sane initial fit. Approximate nearest-neighbor search does not serve exact canonical comparison or deterministic safety rules and adds an irrelevant index/runtime surface.

## Smallest meaningful prototype hypothesis

Build a standalone Rust CLI and black-box harness in the assigned trial output directory, using only the standard library if feasible. The prototype should prioritize a well-tested vertical slice: safe snapshot traversal and include handling, bounded parsing of the declared record forms, stable canonicalization and JSON, exact change/TTL detection, representative delegation/glue and SOA verdicts, baseline coexistence, and atomic publication with fault injection. Where the full declared grammar or 10,000-zone corpus cannot be completed within the trial, the report must identify the exact unsupported boundary and block safely rather than silently accept it.

## Post-review scope correction

The original phrase “safe snapshot traversal” was too broad. The standard-library prototype canonicalizes and checks a path, then opens that path by name. That protects ordinary immutable fixtures against lexical escape and pre-existing symlink escape, but it is a check-then-open sequence and is not race-safe if another process mutates the snapshot concurrently. The honest prototype contract is therefore **immutable, non-racing input snapshot trees for the complete run**. Concurrent input mutation is unsupported and the original race-safe “never read outside either root” requirement remains unproven. No result from this prototype should be used when snapshot immutability cannot be guaranteed; a prospective integration must fail closed by declining to run it in that condition.
